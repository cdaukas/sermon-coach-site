Standing rules. Not tasks, and never completable. They hold whenever the condition applies.

· Never press release in a Preaching Lab. The control renders on an Apprentice seat and no code stops you. That discipline is what stands in for the build, and "held until you release it" is false copy in a Lab, so the page needs its own variant.
· One concern per branch. Step 0 read-only gate, explicit stop conditions, a do-not-touch list, and verification against the live deploy rather than a diff.
· Runtime is the judge. curl -sL, not curl -s. Webhooks fire on production only. Described is not shipped.
· Never run supabase db push. Write the migration file, apply by hand in the SQL editor, repair after.
· The mentee submits their own sermon. That is what a seat is. If the mentor submitted on their behalf there would be no account, no private library, and no seat to sell.
· Never key a write on normalized_email. It is not unique. Use explicit UUIDs. · Homepage additions respect the 9393a9e boundary. No prices, no seat cards, no mailto. A link out to pricing is fine. Anything failing that test belongs on the pricing page. The homepage is src/app/page.tsx composed from src/components/home-v2/*; only public/*.html is static. · Match the case flags between the count you reason from and the check you ship. An expected count derived with grep -oi then verified case-sensitively returned 1 against an expected 3 and looked like a failed deploy. · Two cards with different price grammar invite a false comparison. A bundled total beside a per-unit rate reads as a multiple. Both must headline the same unit before they sit side by side. · A retired checkout param cannot be verified logged out. /checkout?pack=X redirects to /signup?pack=X before validation runs, so a stale link walks a person through account creation before it fails. Verify logged in. · Dead components and dead JS get deleted, not left dark.
